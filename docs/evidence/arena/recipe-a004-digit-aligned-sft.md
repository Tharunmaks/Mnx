# A digit-aligned SFT recipe that should take MNX-cpu from 107/200 to ~120/200

## 0. The short version

The score is stuck for two reasons, and neither of them is the learning rate.

**First, the checkpoint physically cannot write a number it has not memorised.** 1162 of the
tokenizer's 3093 merges are pure digit runs, and the chunking of a number depends on its
*value*: `5384` encodes as `[' 5', '384']` but `4471` as `[' 4', '47', '1']`. To answer
`523855 - 142` the model has to commit to the chunking of the result before it has computed
the result. The base checkpoint's errors are that failure's exact signature — I measured
`523855 - 142 -> 523955` (leading chunk right, tail chunk wrong), `27 + 16 -> 27`,
`13 + 617 -> 617`. After 705k arithmetic examples in pretraining it cannot add two-digit
numbers. That is not a capacity limit, it is a representation limit.

**Second, the trainer bot spends about 95% of the CPU grading instead of learning.** Eight
greedy generations plus eight verification generations buy one gradient step on eight items.
From `runs/bot3_train.log` that is 2680 steps in 1685 s ≈ 12.7 items/s ≈ 100 answer tokens
per second of gradient signal. `runs/cpu/log.csv` shows the same box doing 2050 supervised
tokens per second when the loss is on a packed window. The active-learning loop is paying 20x
for information it could have computed for free: you do not need to quiz the model to learn
that `211654 * 406` has nine digits.

So the recipe is: **re-encode answers one digit per token, put the loss on every position of a
packed window with 4x weight on the answer span, hold the kind mixture perfectly stationary,
anneal only the within-kind difficulty, and spend the saved grading budget on gradients.**
Plus the honest half: multiplication of seven-digit numbers, irreducible fractions and calendar
arithmetic are not learnable here, they are 40% of the arithmetic slice and all of `dates`, and
I reallocate that budget rather than grind on it.

Point estimate: **120/200 (60%)**, range 110–126, with the code / syllogism / primality 100%
kinds protected by a hard abort gate. The gain is ~11 points of `+`/`-` arithmetic, ~2 of
`system2`, ~1 of `gcd`, ~1 of `linear`. Everything else I expect to be flat, and I say where.

## 1. Assumptions

1. "Beats 107/200 on this protocol" means the headline number is
   `scripts/eval_qa.py --ckpt <ckpt> --n 200 --seed 777 --exclude <history>`, unmodified.
2. The checkpoint under test is a fine-tune of `runs/cpu` — no new pretraining run from
   scratch, because the tokenizer and the 10.4M-parameter architecture are given.
3. `mnx/configs.py`, `mnx/model.py`, `mnx/train.py` and `scripts/eval_qa.py` stay as they are.
   The only edit to an existing file is an 11-line, backward-compatible addition to
   `mnx/tokenizer.py`; everything else is one new module.
4. "A few hours" means one unattended run of ≲4 h wall clock on 4 cores, resumable.
5. Numbers I quote as measured were measured on this repository today, on Q&A sets generated
   with seeds **other than 777** (1234, 4242, 99, 31337, 5, 6, 7, 8 — 1600 unseen items

## 2. The constraint box

The design is driven by the tightest constraint in each row, and two of these constraints are
not in the brief — I found them by reading the scorer.

| # | Constraint | Where it binds |
|---|---|---|
| C1 | 4 cores, ~15 GB, no GPU; ≲4 h; resumable | 2050 supervised tokens/s is the entire budget: ~22M tokens for the run. Every token spent on grading or padding is gone. |
| C2 | No pretrained weights, no network, no LLM, no new dependencies | Everything is generated by `mnx/agent/*` at train time; PyTorch + stdlib only. |
| C3 | Never train/tune/memorise eval items; first-run numbers; abstaining = failure | Difficulty must be decided *analytically*, from the generator's own parameters, never from eval performance. Everything trained is logged for `--exclude`. |
| C4 | Must not lose the kinds already at 100% | **100 of the current 107 points are code (80), syllogism (14) and primality (6).** The downside of a bad recipe is −100; the upside is +15. This dominates every trade-off below. |
| **C5** | **`eval_qa.py` takes `out.strip().split("\n")[0]` as the answer** | **No chain of thought, no scratchpad, no reversed digits, no "think then answer". The very first line the model emits must be the exact answer string.** This kills the standard fix for transformer arithmetic and forces everything to be learnable in one forward pass per token, most-significant digit first. |
| **C6** | **The eval set is `stream(600, seed=777)` minus everything excluded, truncated to 200** | Only **277 of the 600** survive the current 3M-pair database (measured). Adding training exclusions therefore *changes which 200 questions are scored*. I estimate ~7 items of drift and handle it by re-scoring the base checkpoint under the identical `--exclude` (§8). |
| C7 | Tokenizer and vocab are frozen at 3355 | Any fix has to work *inside* this tokenizer. The one I use does: a digit-level answer is a different token sequence that `decode()` maps to the identical string. |

## 3. What the 200 questions are actually made of

The brief's per-kind table looks arbitrary until you notice *why* it is shaped like that. The
3M-pair database in `runs/qa` has **exhausted the small-space generators**, so the eval's
`--exclude` filter deletes them entirely:

| generator | distinct questions that exist | in `runs/qa` | items in the 200 |
|---|---:|---:|---:|
| `quadratic` | 325 | 325 | 0 |
| `powers` | ~800 | 798 | 0 |
| `leap` | 801 | 801 | 0 |
| `sequences` | ~3.4k | 3399 | 0 |
| `units` | ~36k | 35725 | 0 |
| `dates`, weekday subtype | 73,000 | ~117k draws | ~1.7 of the 17 |
| `syllogism`, 2 of 3 templates | ~45k | exhausted | 0 (all 84 surviving syllogisms I sampled are the one "Yes, X is a Y." template) |
| `code`, `arithmetic` | astronomically many | 1.03M / 0.71M | 80 and 63 |

Five of the fifteen generators — 18% of the generator weight — contribute **zero** eval items.
That is already a budget reallocation the recipe has to respect.

I then ran the base checkpoint over 1600 pooled unseen items (seeds ≠ 777) to see *what kind of
wrong* it is. This is the most useful thing I measured:

| slice | base | what it emits |
|---|---|---|
| `primality` | 11/12 | **"no" to all twelve**, including the one gold `yes`. 49 of 52 surviving primality items are `no`. |
| `gcd` | 8/10 | correct whenever gcd ∈ {1, 2}; `gcd(6,462)=6 -> 2`, `gcd(369,27)=9 -> 1` |
| `arithmetic +` | 0/10 | `27+16 -> 27`, `13+617 -> 617`, `166+994 -> 977`, `362227+409863 -> 1058967` |
| `arithmetic -` | 0/8 | `523855-142 -> 523955`, `523-20 -> 523`, `117-15 -> 128`, `-305-10 -> -307` |
| `arithmetic *` | 0/6 | `10186*901 -> 1058977` (right digit count, wrong number) |
| `dates` | 0/8 | `2084-02-30` (not a date), and `1341 days` twice for different questions |
| `factorise` | 0/6 | degenerates into `3 × 3 × 3 × 3 × ...` and hits the eval's 40-token cap |
| `system2` | 0/5 | copies numbers off the right-hand side: `3x+y=-6, x-y=-10 -> x = -6, y = -10` |

Three conclusions, each of which changes the recipe:

**(a) `primality` 6/6 is a class prior, not a skill.** The optimal exact-match policy for
"is n prime?" on these draws is "always no" (90.4% of `randint(2,100000)` are composite; 94% of
the *surviving* items are `no`), and the model has found it. There is nothing to win here and
six points to lose. So `primality` gets 3% maintenance weight at loss weight 1.0 and is on the
abort gate. Any recipe that "teaches primality" is expected to *lower* the score.

**(b) `gcd` is mostly a class prior too.** P(gcd(a,b)=1) ≈ 0.61 and P(≤2) ≈ 0.76 for
a,b ∈ [2,500], and the model already gets those. Real headroom on `gcd` is the ~24% of items
with a non-trivial gcd — about 1.7 of the 7 gcd items in the 200. I claim +1, not +3.

**(c) arithmetic fails in chunks, not in digits.** `523855 - 142 -> 523955` is the model
emitting `[' 523', '955']` where the answer needed `[' 523', '71', '3']`: it got the first
chunk right and then had to guess a *different number of tokens* for the tail. `27 + 16 -> 27`
is it copying an operand because no chunk-level completion is available. This is the mechanism
the whole recipe is built on.

## 4. Three diagnoses, each with its fix

### 4.1 Tokenization decides what arithmetic is learnable

`DEFAULT_PATTERN` makes ` ?\d+` one pre-token and then BPE merges inside it. The result:

```
'Q: what is 913 + 4471\nA: 5384'
 -> ['Q', ':', ' what', ' is', ' 913', ' +', ' 4', '47', '1', '\n', 'A', ':', ' 5', '384']
```

1162 of 3093 merges (38% of the whole merge table) are pure digit runs. For the model, adding
is not "carry digits"; it is "pick one of 1162 chunk tokens, then decide whether another chunk
follows, then pick that one too" — and the correct chunk *arity* is a function of the answer's
value, which is what it was trying to compute. Column alignment, the one thing carry
propagation needs, does not exist in this representation.

**Fix.** Tokenization is not injective into strings. `decode([32,53,51,56,52])` is `" 5384"`
exactly as `decode([tok(' 5'), tok('384')])` is. Byte ids are the identity on ASCII, so
`'0'..'9'` are ids 48–57. Encoding the answer span one digit per token is byte-identical after
`decode`, which means **`scripts/eval_qa.py` needs no change at all** — I am changing what the
model is trained to emit, not how it is scored. Verified round-trip on
`" 5384"`, `" -1234567"`, `" 73/4591"`, `" 2025-03-14"`, `" x = -17, y = 3"`,
`" 2 × 2 × 3 × 1049"`, `" 1234 days"`, `" 37.5 °C"`, `" yes"`,
`" Cannot be determined from the premises."`.

At inference the model is never *forced* to emit digits; it does so because that is the only
convention it was trained on for numeric kinds, and the softmax at the first answer position is
then a 10-way choice instead of a 1162-way one. §8 makes "did it actually adopt the format"
a hard falsifier.

**And the stronger version.** Disabling those 1162 merges in the tokenizer makes the
*question* side digit-aligned too, so the model reads `4471` as four columns instead of three
chunks. I measured the cost of that: token inflation is **+12.4% on code documents, +0.0% on
syllogism, +58% on arithmetic**, and the longest code document goes from 185 to 233 tokens —
still inside `max_seq_len=256`. It also leaves identifier merges (`utf8`, `x2`) alone, because
the rule only matches `^ ?[0-9]+$`. That is cheap enough to try, and it is the single biggest
lever on arithmetic, but it re-tokenizes the inputs that earn the 80 code points. So it runs as
a gated Stage 0 with an automatic fallback (§5.2) rather than as an act of faith.

### 4.2 The collapses were lr-per-supervised-token, not lr

This matters because the previous conclusion — "lr 1e-4 destroys the model, use 1e-5" — fixed
the symptom and thereby guaranteed the "gentle" run would gain nothing. Note that
`runs/cpu/log.csv` shows pretraining *ending* at lr 2.0e-4, i.e. **above** the 1e-4 that
allegedly destroyed it. Learning-rate magnitude is not the explanation.

For Adam the noise injected per step scales like `lr / sqrt(supervised tokens per update)`.
Using the repo's own logs:

| run | lr | passes/batch | supervised tokens per update | `lr/√tokens` | result |
|---|---:|---:|---:|---:|---|
| pretraining, end of cosine | 2.0e-4 | 1 | 2048 (full-token loss) | 4.4e-6 | val 0.85, 107/200 |
| 1480 steps, batch 4, 3 passes | 1e-4 | 3 | ~80 (answer-only, batch 4) | 3.4e-5 (**7.6x**) | **6%** |
| 6735 steps, same | 1e-4 | 3 | ~80 | 3.4e-5 | **4%** |
| 1500 steps, batch 8, 1 pass | 1e-5 | 1 | ~160 | 7.9e-7 (0.18x) | 54%, no change |
| **this recipe** | **3e-4 peak** | **1** | **8192** | **3.3e-6 (0.75x)** | — |

The collapsed runs were 7.6x past the operating point pretraining ended at. The "gentle" run
was 5.7x *below* it, which is why it moved nothing. This recipe sits at 0.75x: the largest
learning rate that is still inside the regime the checkpoint was built in. Two further
contributors to the collapse, both removed here:

- **Non-stationary kind marginal.** Curriculum level 1 is `("arithmetic", "leap", "units")`.
  Training answer-only loss on that for an hour re-specialises the output head; the replay fix
  helped but still left the marginal drifting with the level. Here the marginal over kinds is a
  *constant* for the whole run and only the within-kind difficulty anneals.
- **No LM anchor.** Pretraining put loss on every token of a packed window; the bot puts loss
  only on answer tokens. That is two simultaneous shifts. Here the loss is on every token
  (weight 1.0, the pretraining objective) with 4.0 on the answer span of target kinds only —
  measured as **38% of the gradient mass on answers, 62% on the original objective**. The
  anchor kinds get weight 1.0 everywhere, i.e. they are replayed under exactly the objective
  that produced them.
- **Fresh Adam moments.** With zero-initialised `m`/`v`, bias correction makes step 1's update
  ≈ `lr * sign(g)` on all 10.4M coordinates regardless of gradient size. 150 steps of linear
  warmup removes that; the bot has no warmup.

### 4.3 What a 10M model cannot do here, and what I do with the budget

Measured composition of the arithmetic slice (466 unseen items):

| op | share | answer shape | verdict |
|---|---:|---|---|
| `+` | 20.8% | 2–7 digits | **learnable** (target) |
| `-` | 20.0% | 2–7 digits | **learnable** (target) |
| `*` | 39.7% | 19% ≤4 digits, 81% are 5–13 digits | ≤4-digit products targeted; the rest **not learnable** |
| `/` | 19.5% | 82% irreducible fractions (`73/4591`), 8% decimals, 10% integers | exact division targeted; the rest **not learnable** |

So **41% of the arithmetic slice is `+`/`-`** — about 26 of the 63 items — and that is where
the budget goes. Declared not learnable at 10.4M parameters with constraint C5 (answer first,
no scratchpad):

- **7-digit × 7-digit products.** 13 output digits, each a function of all 14 input digits,
  emitted most-significant-first. No amount of data fixes the fact that digit 1 of the answer
  requires the whole convolution.
- **Reduced fractions.** `Fraction(a,b)` for 7-digit a,b requires a gcd *and* then MSB-first
  division. Two impossible things in series.
- **`dates`.** Both surviving subtypes ("how many days between D1 and D2", 47%; "what date is
  N days after D", 43%) need a 73,000-entry date→day-number map followed by MSB-first
  arithmetic. The base model's `2084-02-30` and its reuse of `1341 days` for two different
  questions show it has no calendar at all. 16 points sit here and I am not claiming them.
  `dates` keeps 2% maintenance weight so answers stay date-shaped, nothing more.
- **`factorise`.** Trial division over an unbounded factor list. It also hits the eval's
  40-token cap once digits are split: the worst case `32768 = 2^15` needs 43 tokens. ~1 item,
  currently 0, and I claim 0.
- **`lcm`.** Product-sized output. 37% of `gcd_lcm`; 15% maintenance weight only.
- **`percent`** where `p*n/100` is a fraction: dropped to trace.

Reallocated to: `+`/`-` (the shared bottleneck), small products, exact division, `gcd`,
`linear`, `system2`. **`system2` is the interesting one**: `x, y ∈ [-20, 20]`, coefficients from
`{1,2,3,-1}`, so every intermediate magnitude is ≤ 80 and the output space is 1681 pairs. The
only reason it is 0/6 is that small-integer arithmetic does not exist in this model. It is
downstream of the same fix, which is exactly why concentrating on small-integer arithmetic is
better than spreading the budget: **`system2`, `linear`, `gcd` and `percent` all bottleneck on
it.**

## 5. The recipe

### 5.1 One command

```bash
# Stage 0 (gated): re-align to digit-level tokenization without pushing new skills
python -m mnx.recipe --ckpt runs/cpu --out runs/sft0 --steps 400 \
    --lr 1e-4 --min-lr 1e-5 --warmup 60 --probe-interval 200 --digit-tokenizer

# Stages 1-3: the real run
python -m mnx.recipe --ckpt runs/sft0/ema --out runs/sft --steps 2700 \
    --batch-size 16 --grad-accum 2 --seq-len 256 \
    --lr 3e-4 --min-lr 1e-5 --warmup 150 --weight-decay 0 --grad-clip 1.0 \
    --trip-mult 5 --ema-decay 0.999 \
    --probe-interval 300 --probe-n 128 --save-interval 150 \
    --threads 4 --seed 0 --digit-tokenizer

# evaluate the EMA, with everything the run touched excluded
python scripts/eval_qa.py --ckpt runs/sft/ema --n 200 --seed 777 \
    --exclude runs/sft0/qa_history.jsonl --exclude runs/sft/qa_history.jsonl
```

`--resume` is automatic: re-running the same `--out` picks up the atomic checkpoint, the
optimizer state, the EMA and the data stream's RNG state. SIGINT saves and exits.

### 5.2 The gate and the fallback (this is the safety design, not a footnote)

Stage 0 exists only to answer one question with a number: *does digit-level input tokenization
cost the code points?* It trains 400 steps at a deliberately small lr on the same mixture, and
the probe at step 200 and 400 reports the `code` and `syllogism` slices.

- **Gate passes** (code slice ≥ start − 1 item): run Stages 1–3 with `--digit-tokenizer`.
- **Gate fails**: drop `--digit-tokenizer` everywhere and run Stages 1–3 straight from
  `runs/cpu`. The answer side is still digit-aligned (that needs no tokenizer change and
  cannot alter the code prompts at all, because code answers are excluded from
  `DIGIT_KINDS`), so the main mechanism survives; only the input-side alignment is lost.
  Cost of finding out: ~27 minutes.

The loop also aborts itself mid-run if any probe shows `code`, `syllogism` or `primality` more
than one item below where they started, leaving the last EMA checkpoint as the deliverable. An
abort is a reportable result, not something to retry quietly.

### 5.3 Every hyperparameter, and why

| knob | value | why this value and not another |
|---|---|---|
| steps | 2700 (+400 Stage 0) | 2700 × 8192 tokens = 22.1M supervised tokens ≈ 3 h at the 2050 tok/s the box did during pretraining; 1.7x the pretraining budget, on a third as many kinds. |
| micro-batch | 16 windows × 256 tokens | Largest shape that keeps peak RAM (logits are 16×256×3355 floats, twice) comfortably under 2 GB, and good GEMM shapes on 4 cores. |
| grad accumulation | 2 | 8192 supervised tokens per update = 4x pretraining's 2048. This is the denominator in §4.2: it is what makes lr 3e-4 safe. |
| passes per batch | **1** | The 6% and 4% collapses both used 3. Repeating a batch multiplies the per-token update without adding information; with 8192 fresh tokens per step there is no reason to re-use any of them. |
| sequence length | 256 | `max_seq_len`; unchanged. The longest document under digit tokenization is 233 tokens, so nothing is truncated. |
| lr | 3e-4 peak | `lr/√tokens` = 3.3e-6 = 0.75x of where pretraining's cosine ended (§4.2). The largest rate inside the regime that built this checkpoint. |
| schedule | linear warmup 150, cosine to min_lr 1e-5 | Warmup kills Adam's scale-free first step on fresh moments. Cosine-to-near-zero means the last ~300 steps barely move the weights, so the run ends in a flat region instead of mid-stride. |
| optimizer | AdamW, β=(0.9, 0.95), eps default | Identical to `mnx/train.py`'s pretraining settings. Changing the optimizer would confound the experiment. |
| weight decay | **0.0** | Pretraining used 0.1 with 15 kinds pushing back on every weight. Here code is 22% of the mixture, so 0.1 would shrink the code pathway by ~5% over the run with nothing restoring it — decay *is* a forgetting term when the data no longer covers what the weights encode. |
| grad clip | 1.0 (same as pretraining) + skip any step whose pre-clip norm > 5x the running median of the last 200 | Clipping bounds a bad batch's direction but not its influence. The trip-wire bounds its influence too. Directly aimed at "one impossible batch moved the model and it never came back". |
| EMA | decay 0.999, evaluated and shipped | The saved model becomes an average over ~700 steps, so no single stretch of batches can own the checkpoint. 42 MB. This is the cheapest insurance against the measured failure mode. |
| answer loss weight | 4.0 on target kinds, 1.0 elsewhere | Measured outcome: 38% of gradient mass on answers, 62% on the pretraining objective. Answer-only loss (weight 0 on prompts) was one of the two shifts that broke the bot. |
| loss normaliser | a constant `batch × seq × accum`, not the micro-batch's own weight mass | So accumulated micro-batches sum to the true weighted mean and the logged loss is comparable step to step. |
| probe | 128 held-out items every 300 steps, greedy | ~1.5 min each, ~15 min total — versus the bot's ~95%. Used as a trip-wire and a falsifier only, never to pick a checkpoint. |
| checkpoint selection | **fixed in advance: the final-step EMA** | No selection over probes, so no selection effect to report. The raw final weights are reported alongside as a diagnostic. |
| save interval | 150 steps, atomic + RNG state | ≲10 min of work lost to a kill. |
| threads | 4 | C1. |

### 5.4 The data, in proportion

Fixed for the whole run. The marginal over kinds never moves; this is the fix for the
curriculum collapse.

| group | kind | weight | loss weight on answer | digit-aligned answer |
|---|---|---:|---:|---|
| **anchor** (30%) | `code` | 0.22 | 1.0 | no — left byte-for-byte as pretraining had it |
| | `syllogism` | 0.05 | 1.0 | no |
| | `primality` | 0.03 | 1.0 | yes (answer is `yes`/`no`, so a no-op) |
| **target** (60%) | `arithmetic` | 0.30 | 4.0 | yes |
| | `system2` | 0.10 | 4.0 | yes |
| | `gcd_lcm` | 0.08 | 4.0 | yes |
| | `linear` | 0.06 | 4.0 | yes |
| | `percent` | 0.03 | 4.0 | yes |
| | `factorise` | 0.03 | 4.0 | yes |
| **maintenance** (10%) | `dates` | 0.02 | 1.0 | yes |
| | `leap`, `powers`, `sequences` | 0.02 each | 1.0 | yes |
| | `units`, `quadratic` | 0.01 each | 1.0 | yes |

The maintenance group has **zero mass on this eval** (§3). It costs 10% of the budget and I keep
it deliberately: the eval cannot see `powers`, `units`, `sequences`, `quadratic` or `leap`, and
dropping them would quietly degrade the product for a score that would not notice. That is a
choice, stated, not an accident.

Within a kind, a **learnability gate** decides what to keep. It consults the generator's own
numbers and never the model — which is the whole point, because `retire_after` failures is a
very slow way to discover something `len(str(a*b))` already knows. Items that fail the gate stay
in at 2% ("trace") so the model keeps answering them in the right *shape* rather than going out
of distribution and producing something stranger than a wrong number.

| kind | kept | trace only |
|---|---|---|
| `arithmetic` | `+`/`-` with max operand ≤ the stage cap; `*` with ≤ `mul_digits` digits of product; `/` when exact | everything else |
| `gcd_lcm` | all `gcd`; `lcm` with ≤3-digit answer | larger `lcm` at 15% |
| `system2` | `|x|,|y|` ≤ stage cap | wider solutions |
| `percent` | integer / terminating answers | `p·n/100` fractions |
| `factorise` | ≤3 factors, each ≤3 digits | longer factorisations |
| others | everything | — |

Measured effect of the gate on the arithmetic op mix: from +21% / −20% / ×40% / ÷20% to
**+38% / −39% / ×19% / ÷5%** at stage 1. Rejection sampling on the generators' own output (not
a re-implemented generator) guarantees the question surface forms and answer formats are
identical to the eval's within every accepted slice.

Difficulty anneals in three stages — **only the within-kind caps move, never the kind weights**:

| stage | steps | `+`/`-` max operand | max product digits | `system2` max |x|,|y| |
|---|---|---:|---:|---:|
| 1 | 0–890 | 1,000 | 3 | 9 |
| 2 | 890–1890 | 100,000 | 4 | 20 |
| 3 | 1890–2700 | 1,000,000 | 4 | 20 |

Three-digit columns first, because carry propagation at width 3 is depth-2 lookahead and is
where the skill either appears or does not; widening later reuses the same circuit instead of
asking for it and a length generalisation at once.

### 5.5 What changes in the loop, summarised

1. **Grading → analytic triage.** The quiz/grade/re-quiz cycle is gone from the training step.
   `grade_prediction`'s token-F1 is also the wrong objective: the eval is exact match, and
   F1 0.9 on `523955` vs `523713` is worth exactly zero points. Difficulty comes from
   `accept()`, which reads the generator's numbers.
2. **Per-item batches → packed windows with per-token weights.** Every position produces loss.
   Items are never split across a window boundary, so an answer is never cut in half. Measured
   padding waste: 12.4%.
3. **Answer-only mask → weighted loss.** 1.0 on prompts (the pretraining objective, as an
   anchor), 4.0 on target answers.
4. **Digit-aligned answer encoding** for numeric kinds; code and syllogism untouched.
5. **Curriculum over kinds → stationary mixture + within-kind difficulty anneal.**
6. **Added:** warmup, EMA, a grad-norm trip-wire, a held-out probe with a hard abort gate,
   RNG-state resumability, and `qa_history.jsonl` logging of every trained *and* probed question.
7. **Removed:** `--active-epochs` (>1 is the measured poison), `pass_mark`, `retire_after`,
   `replay_ratio`, the prioritized replay buffer, the five-level curriculum, `--sleep-ms`.

`mnx/trainer_bot.py` is not deleted. It remains the right tool for the 24/7 maintenance job it
was written for; it is the wrong tool for moving a score, for the reasons above.

## 6. Cost comparison with the loop it replaces

| | trainer bot (gentle, 1500 steps) | this recipe (2700 steps) |
|---|---:|---:|
| wall clock (from `runs/bot3_train.log` / `runs/cpu/log.csv`) | ~16 min | ~3 h 10 min |
| forward passes spent grading | ~16 per update | 0 (plus 9 probes of 128 items) |
| supervised tokens per update | ~160 (answer-only, batch 8) | 8192 |
| total supervised tokens | ~0.2 M | **22.1 M** |
| gradient mass on answer tokens | 100% of a tiny amount | 38% of a large amount; the other 62% is the pretraining objective |

"""Digit-aligned supervised fine-tuning for the 10M ``cpu`` checkpoint.

This replaces ``mnx.trainer_bot`` as the *improvement* loop (the bot stays as the
24/7 maintenance loop). Three things change, each because of a measurement:

1. **Answers are tokenised one digit per token.** The checkpoint's BPE spends
   1162 of its 3093 merges on pure digit runs, and the chunk boundaries depend
   on the *value*: ``5384 -> [' 5', '384']`` but ``4471 -> [' 4', '47', '1']``.
   To answer ``523855 - 142`` the model must pick the right chunking of the
   result before it has computed the result. Measured signature of exactly that
   failure on the base checkpoint: ``523855 - 142 -> 523955`` (first chunk
   right, tail chunk wrong), ``27 + 16 -> 27``. Re-encoding the answer span as
   single-digit tokens is byte-identical after ``decode``, so the eval protocol
   does not change at all -- only what the model is asked to emit.

2. **The budget goes into gradients, not into grading.** The trainer bot spends
   ~16 of every 17 forward passes quizzing and re-quizzing the model (8 greedy
   generations + 8 verification generations per single update on 8 items). A
   packed, weighted-loss step puts a loss on every position, so an hour of CPU
   buys roughly 20x more supervised tokens. Difficulty is decided analytically
   (we know ``a*b`` has 13 digits without asking the model), so the quiz is
   demoted to a periodic held-out probe.

3. **The kind mixture is stationary; only difficulty anneals.** The measured
   collapses (54% -> 6% -> 4%) came from narrowing the training distribution to
   one curriculum level while taking ~80 supervised tokens per update at
   lr 1e-4 with 3 passes over the same 4 items. Here the marginal over kinds is
   fixed for the whole run, every step sees ~8k supervised tokens, and the
   anchored kinds (code, syllogism, primality) are 30% of every batch.

    python -m mnx.recipe --ckpt runs/cpu --out runs/sft --steps 2700 --threads 4
    python -m mnx.recipe --out runs/sft --resume            # after any kill
    python -m mnx.recipe --out runs/sft --status

The run is resumable (atomic checkpoints + RNG state), logs every question it
trained on to ``<out>/qa_history.jsonl`` so that ``scripts/eval_qa.py
--exclude`` can drop them, and writes an EMA checkpoint to ``<out>/ema`` which
is the checkpoint to evaluate.

# --------------------------------------------------------------------------
# 1. digit-aligned encoding of the answer span
# --------------------------------------------------------------------------
# Byte ids are the identity on ASCII, so '0'..'9' are 48..57 and '-' is 45.
# Building the answer out of those ids bypasses BPE for digit runs; decode()
# only concatenates bytes, so the resulting string is byte-identical to the
# gold answer and ``scripts/eval_qa.py`` needs no change.
_DIGIT_SPLIT = re.compile(r"([0-9])")


def encode_answer(tok: BPETokenizer, text: str, digitwise: bool) -> List[int]:
    """Encode an answer span, one token per digit when ``digitwise``."""
    if not digitwise:
        return tok.encode(text, allow_special=False)
    ids: List[int] = []
    for part in _DIGIT_SPLIT.split(text):
        if not part:
            continue
        if len(part) == 1 and part.isdigit():
            ids.append(ord(part))
        else:
            ids.extend(tok.encode(part, allow_special=False))
    return ids


def digit_merge_ranks(tok: BPETokenizer) -> List[int]:
    """Ranks of every merge whose token is a pure digit run (optionally space-led).

    Disabling these in the tokenizer makes *both* sides of the pair digit
    aligned (see ``--digit-tokenizer``); identifier merges such as ``utf8`` are
    left alone because they do not match the pattern.
    """
    out = []
    for rank in range(len(tok.merges)):
        piece = tok.vocab[tok.merge_base + rank]
        if re.fullmatch(rb" ?[0-9]+", piece):
            out.append(rank)
    return out


def self_check(tok: BPETokenizer) -> None:
    """Fail loudly at startup if the digit trick does not round-trip."""
    for s in (" 5384", " -1234567", " 73/4591", " 2025-03-14", " x = -17, y = 3",
              " 2 × 2 × 3 × 1049", " 1234 days", " 37.5 °C", " yes",
              " Cannot be determined from the premises."):
        if tok.decode(encode_answer(tok, s, True)) != s:
            raise RuntimeError(f"digit-aligned encoding does not round-trip for {s!r}")

# 2. the mixture: fixed kind weights, annealed within-kind difficulty

# Weights are chosen from the measured composition of the unseen-Q&A set

    "code": 0.22,
    "syllogism": 0.05,
    "primality": 0.03,
    # targets: small-integer arithmetic and the three kinds that are bottlenecked on it
    "arithmetic": 0.30,
    "system2": 0.10,
    "linear": 0.06,
    "gcd_lcm": 0.08,
    "percent": 0.03,
    "factorise": 0.03,
    # maintenance only: zero or near-zero mass on this eval, kept so the product
    # does not regress on skills the eval cannot see (4% of the budget, by choice)
    "dates": 0.02,
    "leap": 0.02,
    "powers": 0.02,
    "sequences": 0.02,
    "units": 0.01,
    "quadratic": 0.01,
}

# 4x gradient weight on the answer span of the kinds we are trying to move;
# 1x (= the pretraining objective) everywhere else, so nothing is pushed.
ANSWER_WEIGHT: Dict[str, float] = {
    "arithmetic": 4.0, "system2": 4.0, "linear": 4.0,
    "gcd_lcm": 4.0, "percent": 4.0, "factorise": 4.0,
}

# Kinds whose answers get digit-aligned encoding. Code and syllogism are left
# exactly as the pretraining tokenised them: they are at 100% and must not move.
DIGIT_KINDS = frozenset({"arithmetic", "system2", "linear", "gcd_lcm", "percent",
                         "factorise", "powers", "sequences", "dates", "units",
                         "quadratic", "primality", "leap"})

TRACE = 0.02   # acceptance for items whose exact answer a 10M model cannot compute
_INT = re.compile(r"-?\d+")
_IS_INT = re.compile(r"-?\d+\Z")


@dataclass
class Stage:
    """One phase of the within-kind difficulty anneal. Kind weights never change."""
    until: float          # fraction of total steps this stage ends at
    addsub_cap: int       # max |operand| for accepted + and - items
    mul_digits: int       # max digits in an accepted product
    sys_cap: int          # max |x|,|y| for accepted 2x2 systems


STAGES: Tuple[Stage, ...] = (
    Stage(until=0.33, addsub_cap=1_000,   mul_digits=3, sys_cap=9),
    Stage(until=0.70, addsub_cap=100_000, mul_digits=4, sys_cap=20),
    Stage(until=1.01, addsub_cap=1_000_000, mul_digits=4, sys_cap=20),
)


def _arith_op(q: str) -> str:
    if " plus " in q or " + " in q:
        return "+"
    if " minus " in q or " - " in q:
        return "-"
    if " times " in q or " * " in q:
        return "*"
    return "/"


def accept(kind: str, q: str, a: str, st: Stage) -> float:
    """Probability of keeping a freshly generated item: the learnability gate.

    Nothing here consults the model. The generator's own numbers tell us whether
    the answer is computable in one forward pass per token at 10M parameters:
    a 13-digit product and an irreducible 7-digit fraction are not, and
    ``retire_after`` failures is a slow way to discover what arithmetic already
    knows. Impossible items stay in at ``TRACE`` so the model keeps answering
    them in the right shape instead of going out of distribution.
    """
    if kind == "arithmetic":
        op = _arith_op(q)
        body = q[:-3] if q.rstrip().endswith("= ?") else q
        nums = [abs(int(n)) for n in _INT.findall(body)]
        if op in "+-":
            return 1.0 if (nums and max(nums) <= st.addsub_cap) else TRACE
        if op == "*":
            return 1.0 if (_IS_INT.match(a) and len(a.lstrip("-")) <= st.mul_digits) else TRACE
        return 1.0 if _IS_INT.match(a) else TRACE          # exact division only
    if kind == "gcd_lcm":
        if "gcd" in q or "greatest" in q:
            return 1.0
        return 1.0 if len(a) <= 3 else 0.15                 # lcm: only the small ones
    if kind == "system2":
        xs = [abs(int(n)) for n in _INT.findall(a)]
        return 1.0 if (xs and max(xs) <= st.sys_cap) else TRACE
    if kind == "percent":
        return 1.0 if ("/" not in a) else TRACE             # drop p*n/100 fractions
    if kind == "factorise":
        f = a.split(" × ")
        return 1.0 if (len(f) <= 3 and max(len(x) for x in f) <= 3) else TRACE
    return 1.0                                              # anchors + maintenance


class MixtureStream:
    """Endless shaped Q&A, reproducible and resumable.

    ``forbidden`` holds the hashes of the held-out probe questions so the probe
    stays a true holdout.
    """

    def __init__(self, seed: int = 0, forbidden: Optional[set] = None):
        self.rng = random.Random(seed)
        self.forbidden = forbidden or set()
        self.banned = _held_out_names()
        self.kinds = list(KIND_WEIGHTS)
        self.weights = [KIND_WEIGHTS[k] for k in self.kinds]
        self.drawn = 0
        self.rejected = 0

    def state(self) -> dict:
        st = self.rng.getstate()
        return {"rng": [st[0], list(st[1]), st[2]], "drawn": self.drawn, "rejected": self.rejected}

    def load_state(self, d: dict) -> None:
        v, ints, gauss = d["rng"]
        self.rng.setstate((v, tuple(ints), gauss))
        self.drawn = d.get("drawn", 0)
        self.rejected = d.get("rejected", 0)

    def one(self, st: Stage) -> dict:
        kind = self.rng.choices(self.kinds, self.weights)[0]
        gen = GENERATORS[kind][1]
        q = a = ""
        for _ in range(64):
            q, a = gen(self.rng, self.banned) if kind == "code" else gen(self.rng)
            if hash(q) in self.forbidden:
                self.rejected += 1
                continue
            w = accept(kind, q, a, st)
            if w >= 1.0 or self.rng.random() < w:
                break
            self.rejected += 1
        self.drawn += 1
        return {"q": q, "a": a, "kind": kind}


# --------------------------------------------------------------------------
# 3. packing with per-token loss weights
# --------------------------------------------------------------------------
def encode_item(tok: BPETokenizer, it: dict, digitwise: bool) -> Tuple[List[int], List[float]]:
    """``<bos> Q: ...\\nA: <answer>\\n<eos>`` plus a per-token loss weight.

    The document shape is the pretraining shape (``as_document`` + packing), so
    the anchor kinds see exactly the objective they were trained on. Only the
    answer weight and the digit alignment differ, and only for target kinds.
    """
    prompt = [tok.bos_id] + tok.encode(PROMPT.format(q=it["q"]), allow_special=False)
    use_digits = digitwise and it["kind"] in DIGIT_KINDS
    ans = encode_answer(tok, " " + it["a"] + "\n", use_digits) + [tok.eos_id]
    aw = ANSWER_WEIGHT.get(it["kind"], 1.0)
    return prompt + ans, [1.0] * len(prompt) + [aw] * len(ans)


def pack(draw: Callable[[], Tuple[dict, List[int], List[float]]],
         seq_len: int, pad_id: int, n_windows: int
         ) -> Tuple[torch.Tensor, torch.Tensor, torch.Tensor, List[dict]]:
    """Greedily pack whole items into ``n_windows`` windows of ``seq_len + 1``.

    ``draw()`` returns ``(item, ids, weights)`` and is called until the windows
    are full, so a micro-batch is always full regardless of how long the code
    items happen to be. Items are never split across a window boundary, so an
    answer is never cut in half; the tail of a window is padded and carries
    weight 0. Dense packing matches how this checkpoint was pretrained (several
    documents per window, causal attention across them).
    """
    want = seq_len + 1
    x = torch.full((n_windows, want), pad_id, dtype=torch.long)
    y = torch.full((n_windows, want), -100, dtype=torch.long)
    wt = torch.zeros((n_windows, want), dtype=torch.float32)
    used: List[dict] = []
    carry: Optional[Tuple[List[int], List[float]]] = None
    for r in range(n_windows):
        ids: List[int] = []
        ws: List[float] = []
        if carry is not None:
            ids, ws = carry
            carry = None
        while len(ids) < want:
            it, i2, w2 = draw()
            i2, w2 = i2[:want], w2[:want]
            used.append(it)
            if len(ids) + len(i2) > want:
                carry = (i2, w2)                 # starts the next window
                break
            ids.extend(i2)
            ws.extend(w2)
        n = len(ids)
        x[r, :n] = torch.tensor(ids, dtype=torch.long)
        y[r, :n] = torch.tensor(ids, dtype=torch.long)
        wt[r, :n] = torch.tensor(ws, dtype=torch.float32)
    return x[:, :-1].contiguous(), y[:, 1:].contiguous(), wt[:, 1:].contiguous(), used

class EMA:
    """Weight average over the last ~1/(1-decay) steps.

    The measured failure mode of this checkpoint is that a bad stretch of
    batches moves it out of a good basin and it never comes back. An EMA makes
    the *saved* model an average over ~700 steps, so no single stretch can own
    the checkpoint.
    """

    def __init__(self, model: torch.nn.Module, decay: float):
        self.decay = decay
        self.n = 0
        self.shadow = {k: v.detach().clone().float() for k, v in model.state_dict().items()}

    def update(self, model: torch.nn.Module) -> None:
        self.n += 1
        d = min(self.decay, (1.0 + self.n) / (10.0 + self.n))   # warm up the average
        for k, v in model.state_dict().items():
            s = self.shadow[k]
            if v.dtype.is_floating_point:
                s.mul_(d).add_(v.detach().float(), alpha=1.0 - d)
            else:
                s.copy_(v)

    def state_dict(self) -> dict:
        return {"n": self.n, "shadow": self.shadow}

    def load_state_dict(self, d: dict) -> None:
        self.n = d["n"]
        self.shadow = d["shadow"]

    def apply_to(self, model: MNXCoder) -> dict:
        ref = model.state_dict()
        return {k: v.to(dtype=ref[k].dtype) for k, v in self.shadow.items()}


def cosine_lr(step: int, total: int, lr: float, min_lr: float, warmup: int) -> float:
    if warmup > 0 and step < warmup:
        return lr * (step + 1) / warmup
    if step >= total:
        return min_lr
    p = (step - warmup) / max(1, total - warmup)
    return min_lr + 0.5 * (lr - min_lr) * (1.0 + math.cos(math.pi * p))


# ---- the held-out probe: our own data, never trained on, logged for --exclude
PROBE_SLICES = ("addsub_small", "addsub_big", "mul_small", "gcd", "system2", "linear", "code",
                "syllogism", "primality", "dates")


def probe_slice(it: dict) -> Optional[str]:
    k = it["kind"]
    if k == "arithmetic":
        op = _arith_op(it["q"])
        body = it["q"][:-3] if it["q"].rstrip().endswith("= ?") else it["q"]
        nums = [abs(int(n)) for n in _INT.findall(body)]
        if op in "+-":
            return "addsub_small" if (nums and max(nums) <= 1000) else "addsub_big"
        if op == "*" and _IS_INT.match(it["a"]) and len(it["a"].lstrip("-")) <= 4:
            return "mul_small"
        return None
    if k == "gcd_lcm":
        return "gcd" if ("gcd" in it["q"] or "greatest" in it["q"]) else None
    return k if k in PROBE_SLICES else None


def build_probe(n: int, seed: int) -> List[dict]:
    """A held-out set from the same generators, balanced over the slices we claim."""
    rng = random.Random(seed)
    banned = _held_out_names()
    per = max(1, n // len(PROBE_SLICES))
    want = {s: per for s in PROBE_SLICES}
    out: List[dict] = []
    seen = set()
    guard = 0
    while sum(want.values()) > 0 and guard < 400_000:
        guard += 1
        kind = rng.choice(list(KIND_WEIGHTS))
        gen = GENERATORS[kind][1]
        q, a = gen(rng, banned) if kind == "code" else gen(rng)
        s = probe_slice({"q": q, "a": a, "kind": kind})
        if s is None or want.get(s, 0) <= 0 or hash(q) in seen:
            continue
        seen.add(hash(q))
        want[s] -= 1
        out.append({"q": q, "a": a, "kind": kind, "slice": s})
    return out

            for p in self.probe:
                f.write(json.dumps({"q": p["q"], "a": p["a"], "kind": p["kind"], "role": "probe"}) + "\n")
        marker.write_text("1")

    def _save(self) -> None:
        tmp = self.dir / (CKPT_NAME + ".tmp")
        torch.save({"model": self.model.state_dict(), "optimizer": self.opt.state_dict(),
                    "ema": self.ema.state_dict(), "config": self.model.cfg.to_dict(),
                    "step": self.step, "stream": self.stream.state(), "gn": self.gn[-200:],
                    "skipped": self.skipped, "train_args": asdict_cfg(self.cfg)}, tmp)
        os.replace(tmp, self.dir / CKPT_NAME)
        ema_dir = self.dir / "ema"
        ema_dir.mkdir(exist_ok=True)
        tmp = ema_dir / (CKPT_NAME + ".tmp")
        torch.save({"model": self.ema.apply_to(self.model), "config": self.model.cfg.to_dict(),
                    "step": self.step}, tmp)
        os.replace(tmp, ema_dir / CKPT_NAME)
        self.tok.save(ema_dir / TOKENIZER_NAME)
        (ema_dir / CONFIG_NAME).write_text(json.dumps(self.model.cfg.to_dict(), indent=2))

    def _load(self) -> None:
        p = self.dir / CKPT_NAME
        if not p.exists():
            return
        st = torch.load(p, map_location="cpu")
        if "ema" not in st:          # a plain pretraining checkpoint, not one of ours
            return
        self.model.load_state_dict(st["model"])
        self.opt.load_state_dict(st["optimizer"])
        self.ema.load_state_dict(st["ema"])
        self.step = st["step"]
        self.stream.load_state(st["stream"])
        self.gn = list(st.get("gn", []))
        self.skipped = st.get("skipped", 0)
        print(f"resumed at step {self.step}")

    # ------------------------------------------------------------------ stages
    def stage(self) -> Stage:
        frac = self.step / max(1, self.cfg.steps)
        for s in STAGES:
            if frac < s.until:
                return s
        return STAGES[-1]

    # -------------------------------------------------------------------- loss
    def micro(self, st: Stage) -> Tuple[torch.Tensor, float, List[dict]]:
        def draw():
            it = self.stream.one(st)
            ids, w = encode_item(self.tok, it, self.cfg.digit_answers)
            return it, ids, w
        x, y, w, used = pack(draw, self.cfg.seq_len, self.tok.pad_id, self.cfg.batch_size)
        logits, _, _ = self.model(x)
        ll = F.cross_entropy(logits.view(-1, logits.size(-1)).float(), y.reshape(-1),
                             ignore_index=-100, reduction="none")
        ww = w.reshape(-1)
        # Normalise by a *constant* (not by this micro-batch's weight mass) so
        # accumulated micro-batches add up to the true weighted mean and the
        # logged loss is comparable across steps.
        nominal = self.cfg.batch_size * self.cfg.seq_len * self.cfg.grad_accum
        return (ll * ww).sum() / nominal, float(ww.sum()), used

    def run_step(self) -> dict:
        st = self.stage()
        lr = cosine_lr(self.step, self.cfg.steps, self.cfg.lr, self.cfg.min_lr, self.cfg.warmup)
        for g in self.opt.param_groups:
            g["lr"] = lr
        self.opt.zero_grad(set_to_none=True)
        total = 0.0
        mass = 0.0
        trained: List[dict] = []
        for _ in range(self.cfg.grad_accum):
            loss, m, items = self.micro(st)
            trained.extend(items)
            loss.backward()
            total += float(loss.item())
            mass += m
        gn = float(torch.nn.utils.clip_grad_norm_(self.model.parameters(), self.cfg.grad_clip))
        skip = False
        if len(self.gn) >= 50 and self.step > self.cfg.warmup:
            if gn > self.cfg.trip_mult * statistics.median(self.gn):
                skip = True
                self.skipped += 1
        if not skip:
            self.opt.step()
            self.ema.update(self.model)
        self.gn = (self.gn + [gn])[-200:]
        self.step += 1
        if self.cfg.log_history:
            with (self.dir / "qa_history.jsonl").open("a") as f:
                for it in trained:
                    f.write(json.dumps({"q": it["q"], "a": it["a"], "kind": it["kind"],
                                        "step": self.step}) + "\n")
        row = {"step": self.step, "lr": lr, "loss": round(total, 5), "grad_norm": round(gn, 3),
               "skipped": self.skipped, "weighted_tokens": int(mass), "items": len(trained),
               "addsub_cap": st.addsub_cap, "rejected": self.stream.rejected}
        with (self.dir / "metrics.jsonl").open("a") as f:
            f.write(json.dumps(row) + "\n")
        return row

    # ------------------------------------------------------------------- probe
    @torch.no_grad()
    def run_probe(self, use_ema: bool = True) -> Dict[str, Tuple[int, int]]:
        from mnx.generate import complete
        model = self.model
        backup = None
        if use_ema:
            backup = {k: v.detach().clone() for k, v in model.state_dict().items()}
            model.load_state_dict(self.ema.apply_to(model))
        model.eval()
        res: Dict[str, List[int]] = {s: [0, 0] for s in PROBE_SLICES}
        for it in self.probe:
            n_tok = 120 if it["kind"] == "code" else 40
            out = complete(model, self.tok, PROMPT.format(q=it["q"]), max_new_tokens=n_tok,
                           temperature=0.0)
            if it["kind"] == "code":
                from mnx.agent.skills.neural import run_tests
                tests = [l for l in it["q"].splitlines() if l.startswith("assert ")]
                ok = bool(tests) and run_tests(out.strip() + "\n", tests)[0]
            else:
                ok = out.strip().split("\n")[0].strip() == it["a"].strip()
            r = res[it["slice"]]
            r[0] += 1
            r[1] += int(ok)
        model.train()
        if backup is not None:
            model.load_state_dict(backup)
        out = {k: (v[1], v[0]) for k, v in res.items()}
        with (self.dir / "probe.jsonl").open("a") as f:
            f.write(json.dumps({"step": self.step, "ema": use_ema,
                                "slices": {k: list(v) for k, v in out.items()}}) + "\n")
        return out

    # --------------------------------------------------------------------- run
    def run(self) -> int:
        cfg = self.cfg
        print(f"sft: {cfg.steps} steps, {cfg.batch_size}x{cfg.seq_len}x{cfg.grad_accum} = "
              f"{cfg.batch_size * cfg.seq_len * cfg.grad_accum} tokens/step, lr {cfg.lr:g} "
              f"-> {cfg.min_lr:g}, digit answers {cfg.digit_answers}, probe {len(self.probe)} items",
              flush=True)
        base = self.run_probe(use_ema=False)
        print("probe @ start:", fmt_probe(base), flush=True)
        t0 = time.time()
        while not self.stop and self.step < cfg.steps:
            row = self.run_step()
            if self.step % 25 == 0:
                el = time.time() - t0
                print(f"step {self.step:>5}/{cfg.steps} | lr {row['lr']:.2e} | loss {row['loss']:.4f} "
                      f"| gn {row['grad_norm']:.2f} | skip {row['skipped']} | {el:6.0f}s "
                      f"| {el / max(1, self.step) :.2f}s/step", flush=True)
            if self.step % cfg.probe_interval == 0:
                p = self.run_probe()
                print(f"probe @ {self.step}: {fmt_probe(p)}", flush=True)
                if not self.anchors_ok(p, base):
                    print("ABORT: anchor slice regressed past the gate; the last saved EMA "
                          "checkpoint is the deliverable. Report this abort.", flush=True)
                    self._save()
                    return 2
            if self.step % cfg.save_interval == 0:
                self._save()
        self._save()
        print(f"done at step {self.step}; final probe: {fmt_probe(self.run_probe())}")
        print(f"evaluate: {self.dir / 'ema'}   history: {self.dir / 'qa_history.jsonl'}")
        return 0

    @staticmethod
    def anchors_ok(now: Dict[str, Tuple[int, int]], base: Dict[str, Tuple[int, int]]) -> bool:
        """Hard gate: the anchors may not fall more than 1 item below the start."""
        for s in ("code", "syllogism", "primality"):
            c0, n0 = base.get(s, (0, 0))
            c1, n1 = now.get(s, (0, 0))
            if n0 and n1 and c1 < c0 - 1:
                return False
        return True


def fmt_probe(p: Dict[str, Tuple[int, int]]) -> str:
    return "  ".join(f"{k}={c}/{n}" for k, (c, n) in p.items() if n)

## 8. The measurement plan

### 8.1 The four numbers that matter

Run these in order. **The paired re-score in row 1 is not optional**, for the reason in C6: the
new exclusions change which 200 questions are scored, so the only honest comparison is
base-vs-new on one identical set.

| # | command | what it is |
|---|---|---|
| 1 | `eval_qa.py --ckpt runs/cpu --n 200 --seed 777 --exclude runs/sft0/qa_history.jsonl --exclude runs/sft/qa_history.jsonl` | **the baseline, re-scored on the same 200 items the new model will see.** Expect ~107 ± 4. |
| 2 | `eval_qa.py --ckpt runs/sft/ema --n 200 --seed 777 --exclude …same flags…` | **the headline.** Compare to row 1, not to the historical 107. |
| 3 | `eval_qa.py --ckpt runs/sft --n 200 --seed 777 --exclude …same flags…` | the raw final weights, as a check that the EMA is helping rather than hiding. |
| 4 | `eval_qa.py --ckpt runs/sft/ema --n 200 --seed 777` (no `--exclude` of the run's history) | the **memorisation gap**: row 4 − row 2. If training produced algorithms, this is ≈ 0. If it is large, the gain is recall of trained items and the recipe is wrong. |

Then, for variance: `--n 600 --seed 777` on rows 1 and 2. At n = 200 the binomial standard
error on a 54% score is 3.5 points, so a 5-point move is 1.4σ — not a result. At n = 600 it is
2.0 points. **Report the per-kind `n` from every run**; if the per-kind counts differ between
rows 1 and 2 the runs are not comparable and the eval must be repeated with identical flags.

Expected exclusion drift, computed per kind from the generators' space sizes against the
~560k questions the run logs: `code` ≈ 4.3 items, `system2` ≈ 0.8, `syllogism` ≈ 0.5,
`gcd_lcm` ≈ 0.5, `primality` ≈ 0.5, `linear` ≈ 0.2, `factorise` ≈ 0.2, arithmetic ≈ 0 —
**≈ 7 of 200 items displaced**. 277 of the 600 survive today, so there are still ≥ 200 after
the drift and the eval will not silently shrink. (If it ever does, `eval_qa.py` prints the
totals per kind and the mismatch is visible.)

### 8.2 The one ablation worth the CPU

`--no-digit-answers`, identical in every other respect, same seed, same step count. This is the
only run that attributes the gain to the mechanism rather than to "more training". If the
ablation moves the score as much as the main run, my diagnosis in §4.1 is wrong and the real
effect was simply 22M more tokens — worth knowing. A 900-step version at one third the cost is
enough to see the arithmetic slices separate.

### 8.3 What falsifies this recipe

Each of these is checkable from the run's own logs, before the eval.

| F | test | threshold | what it means |
|---|---|---|---|
| F1 | **Format adoption.** Fraction of probe answers for numeric kinds whose greedy decode is entirely single-digit tokens. | < 90% at step 900 | The digit convention did not take. The whole mechanism is void; stop, do not spend the remaining 2 h. |
| F2 | **The core claim.** Probe `addsub_small` accuracy. | < 15% at step 900 (one third of the budget) | MSB-first carry is not being learned at 10.4M parameters with this data budget. The +11 arithmetic prediction is falsified; `system2`, `linear` and `gcd` predictions fall with it, since they are downstream. |
| F3 | **The anchors.** Probe `code`, `syllogism`, `primality`. | any of them > 1 item below the step-0 probe | The run aborts itself. Report the abort and the last EMA; do not restart with a lower lr and call it a result. |
| F4 | **The headline.** Row 2 − row 1 of §8.1. | ≤ +3 items (within 1σ) | The recipe did not beat the baseline. |
| F5 | **Honesty.** Row 4 − row 2. | > +3 items | The gain is memorisation of trained questions, not generalisation. Reject the result. |
| F6 | **Stability.** Skipped-step count in `metrics.jsonl`. | > 2% of steps | The gradient distribution is heavy-tailed, i.e. the mixture contains something pathological; the trip-wire is masking a data bug rather than guarding against one. |

A result I would accept as "the recipe works": row 2 − row 1 ≥ +8 items, anchors intact,
memorisation gap ≤ 1 item, and the gain concentrated in `arithmetic` and `system2` as predicted
rather than spread thinly (spread thinly would mean I got the mechanism right by accident).

### 8.4 Wall-clock budget

| step | cost |
|---|---|
| Stage 0 (400 steps + 2 probes) | ~30 min |
| Stages 1–3 (2700 steps + 9 probes) | ~3 h 10 min |
| 4 evals at n=200 (≈14k decoded tokens each) | ~20 min |
| 2 evals at n=600 | ~60 min |
| **total** | **≈ 5 h**, of which the unattended training run is 3 h 40 min and resumable |

Peak RAM: weights 42 MB + EMA 42 MB + Adam state 84 MB + logits 2 × 55 MB ≈ 300 MB plus
PyTorch overhead. Nowhere near the 15 GB limit, which is why the micro-batch is sized for GEMM
shape rather than for memory.

## 9. Expected gain, honestly, per kind

Point estimates, with the floor being "the digit-level representation helps a bit but
MSB-first carry only half-works" and the ceiling being "it works and Stage 0's gate passed".

| kind | n | now | floor | **point** | ceiling | where it comes from |
|---|---:|---:|---:|---:|---:|---|
| `code` | 80 | 80 | 79 | **80** | 80 | Held, not gained. 22% of every batch under the original objective, plus the abort gate. Already saturated; the §"dead ends" list is right that more recipes do nothing. |
| `syllogism` | 14 | 14 | 14 | **14** | 14 | One surviving template, already memorised. Held at 5%. |
| `primality` | 6 | 6 | 5 | **6** | 6 | "Always no" is the optimal exact-match policy and the model has it. Maintenance weight only, specifically so it is *not* taught. |
| `arithmetic` | 63 | 3 | 6 | **14** | 20 | ~14 small `+`/`-` items at ~65%, ~12 large `+`/`-` at ~25%, ~5 small products at ~40%. The mechanism is digit-column alignment; the risk is that MSB-first carry at width 6–7 does not generalise from width 3. |
| `system2` | 6 | 0 | 0 | **2** | 3 | Every intermediate ≤ 80, output space 1681, 10% of the budget. Downstream of small-integer arithmetic, so it moves only if `arithmetic` does. |
| `gcd_lcm` | 11 | 3 | 2 | **4** | 5 | The gcd ∈ {1,2} majority is already right; the gain is the ~24% of gcds that are non-trivial. `lcm` is written off. Note the base model scored 8/10 on gcd in my surrogate sample versus 3/7 at seed 777 — part of the 3/11 is bad luck, so some of this "gain" may be regression to the mean. I flag that rather than bank it. |
| `linear` | 1 | 0 | 0 | **1** | 1 | One small division. Cheap, included because it shares the bottleneck. |
| `dates` | 17 | 1 | 1 | **1** | 2 | **Declared not learnable.** Needs a 73k-date→day-number table plus MSB-first arithmetic. 16 points left on the table on purpose; 2% maintenance weight keeps answers date-shaped. |
| `percent` | 1 | 0 | 0 | **0** | 1 | Two thirds learnable in principle, but it is one item. |
| `factorise` | 1 | 0 | 0 | **0** | 0 | Trial division, unbounded output length, and the eval's 40-token cap bites at `2^15`. |
| **total** | **200** | **107** | **110** | **122** | **132** | |

I would put the recipe at **120 ± 6**, i.e. 60%, and I would be unsurprised by 114. The honest
summary of where the points are:

- **~11 points are one skill**: adding and subtracting integers, which this model has never
  been able to do because it was never asked to emit digits. That is the whole bet.
- **~4 points are downstream** of that skill (`system2`, `linear`, the non-trivial `gcd`s).
- **0 points come from `dates`, `factorise`, `lcm`, large `*` and fractional `/`** — 36 of the
  93 available points — and I am reallocating that budget rather than claiming them.
- **100 points are defended, not earned.** Given that the measured alternative outcomes of
  touching this checkpoint were 6% and 4%, most of the engineering above (stationary mixture,
  weight-1.0 anchor stream, warmup, EMA, trip-wire, abort gate) exists to make sure the 100
  points are still there at the end. A recipe that gains 15 and keeps 100 beats a recipe that
  gains 30 and loses 80, and the measured history of this checkpoint says the second outcome
  is the likely one if you are careless.

### What I am *not* proposing

None of the known dead ends: no hand-written code recipes, no larger program-search budget, no
docstring-example reading, no character-level string ops, no neighbour/all-pairs templates, no
pretrained weights, no downloads, no change to `scripts/eval_qa.py`, and no touching of the
eval set. The code score is already 80/80 on this protocol; there is nothing there to win, and
the §"dead ends" measurements say so.

## 10. Risk register (the things I went looking for)

| risk | why it could bite | what is in the recipe for it |
|---|---|---|
| **The model keeps emitting BPE chunks at inference** | Nothing *forces* digit decoding; it is a learned convention and greedy decoding over the full vocab could still prefer `' 384'`. | F1 is a hard falsifier checked at step 900, not at the end. 60% of items drive the convention, and the first answer token is the decision point. |
| **Digit-level answers overflow the eval's token cap** | `max_new_tokens=40` for non-code; `factorise` of `2^15` needs 43 digit tokens; a looping `factorise` already truncates today. | Quantified: it affects `factorise` only (~1 item, currently 0/1), and `factorise` is gated to ≤3 factors in training so the loop behaviour should improve, not worsen. Not claimed as a gain. |
| **Disabling digit merges breaks the 80 code points** | Code prompts re-tokenize (+12.4% tokens, max doc 185 → 233). | This is the entire reason for the gated Stage 0 and the automatic fallback to answer-only digit alignment (§5.2). 27 minutes buys the answer. |
| **Packed windows put an item at position 150, the eval puts it at 0** | RoPE is not fully position-invariant. | Unchanged from pretraining, which packed the same way and still earns 80/80 and 14/14. Not a new risk. |
| **Training exclusions change the eval set** | Only 277 of the 600 seed-777 questions survive today; ~7 of the 200 get displaced. | The paired re-score (§8.1 row 1) makes both numbers come from one identical set; per-kind `n` is reported for both. |
| **The probe becomes a tuning set** | It decides when the run aborts, so it is selection data. | Probe questions are written to `qa_history.jsonl` and passed to `--exclude`; the training stream refuses any question whose hash is in the probe; the checkpoint rule ("final-step EMA") is fixed in advance so there is no selection over probes. |
| **`primality` gets "taught" and the class prior breaks** | Any gradient pressure toward `yes` loses points, because exact match rewards the degenerate policy. | 3% weight, loss weight 1.0, no gate on it, and it is one of the three abort-gate slices. |
| **An impossible batch wrecks the run** | Measured twice (6%, 4%). | Analytic gate keeps impossible items at 2%; trip-wire skips a step whose pre-clip grad norm exceeds 5x the median; EMA averages ~700 steps; atomic save every 150 steps. |
| **A kill loses hours** | C1 requires resumability. | Model, optimizer, EMA, step, grad-norm history *and* the data stream's RNG state are in one atomic checkpoint; re-running the same `--out` resumes exactly. SIGINT/SIGTERM save first. |
| **The gain is memorisation** | 560k generated items; the small-space kinds repeat. | F5: the memorisation gap (§8.1 row 4 − row 2) must be ≤ 1 item. |
| **My diagnosis is simply wrong** | Possible. | F2 answers it at one third of the budget on held-out data, and §8.2's ablation answers it properly. Both are cheaper than being wrong at the end. |

## 11. If it works, the next thing

Not more recipes. The next 20 points on this protocol are `dates`, and the only way a 10M model
gets them under constraint C5 is if the *answer format itself* carries the computation —
e.g. if `dates` answered `1194 days` by first being taught day-numbers as a first-class answer
kind, so that the calendar map is learned as its own 73k-item skill and the subtraction reuses
the `+`/`-` circuit. That needs a new generator in `mnx/agent/qa_stream.py`, which changes the
eval's own question mix and so is a different conversation — and it should be had explicitly,
not smuggled in.
